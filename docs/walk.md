# The assisted walk

`odo walk` opens the shopping sites in a real browser, reads what's listed, and saves it to the ledger. This page starts with the browser you have to launch, then covers what a walk does, the rules every site shares, what's different about each site, where the recorded pages land, and how the page text becomes vehicle fields.

## Your browser

`odo walk` never launches a browser. It connects over the Chrome DevTools Protocol to a Chrome or Microsoft Edge that you start by hand, in a dedicated profile so it never touches your everyday browsing session. Edge speaks the same protocol as Chrome and is an equally valid choice, so use whichever Chromium browser you actually have installed.

Chrome and Edge each get their own profile directory rather than sharing one, since each browser encrypts its stored cookies with a key only it can read. A bot-defense challenge you clear in one browser still has to be cleared again the first time you switch to the other. If nothing is listening on the debugging port, `odo walk` prints the exact command for your OS and exits, and running `odo walk` again picks it up.

Here are the launch lines, which `odo walk` also prints itself with your own data directory filled in.

**macOS, Chrome**

```
/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome --remote-debugging-port=9222 --user-data-dir="$HOME/Library/Application Support/Odonomics/chrome-profile"
```

**macOS, Edge**

```
/Applications/Microsoft\ Edge.app/Contents/MacOS/Microsoft\ Edge --remote-debugging-port=9222 --user-data-dir="$HOME/Library/Application Support/Odonomics/edge-profile"
```

**Windows (PowerShell), Chrome**

```
& "C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222 --user-data-dir="$env:LOCALAPPDATA\Odonomics\chrome-profile"
```

**Windows (PowerShell), Edge**

```
& "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --remote-debugging-port=9222 --user-data-dir="$env:LOCALAPPDATA\Odonomics\edge-profile"
```

**Windows (cmd), Chrome**

```
"C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222 --user-data-dir="%LOCALAPPDATA%\Odonomics\chrome-profile"
```

**Windows (cmd), Edge**

```
"C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --remote-debugging-port=9222 --user-data-dir="%LOCALAPPDATA%\Odonomics\edge-profile"
```

A bare quoted path needs PowerShell's `&` call operator to run at all, while cmd runs it either way. When `odo walk` can't find a browser listening, it prints all four Windows forms (Chrome and Edge, PowerShell and cmd), and on macOS and Linux it prints both browsers' lines. On Linux those are `google-chrome` and `microsoft-edge`, with the same `--remote-debugging-port=9222` flag and a `--user-data-dir` of `chrome-profile` or `edge-profile` under your data directory.

Leave that window open for as long as you're walking. The one time the browser comes to the front is a bot-defense challenge. The walk beeps and brings the challenged page to the front so you can solve it by hand, then the walk goes back to running in the background once you press Enter. On macOS it also puts your previous window back in front at that point.

## What a walk does

A bare `odo walk` walks the whole shortlist in one command: cars.com first, then Carvana, then Autotrader, then CarMax, then CarGurus. On each site it visits every model in the scenario's `allowedModels`, in order, and it prints which site and model it's about to visit before each one. `odo walk cars.com`, `odo walk carvana`, `odo walk autotrader`, `odo walk carmax`, or `odo walk cargurus` narrows it to that one site, still with every model. `--model "Make Model"` narrows either form to that one model exactly, matching the scenario's own casing case-insensitively; naming a model that isn't a candidate at all and never gets a pair of its own (`--model "Toyota Prius Prime"`, see [below](#rules-every-site-shares)) is refused with a message saying so, the same skip stated plainly rather than attempted.

Every site-and-model pair visits its search page, and a model with a hybrid-only rule gets two of them on cars.com and CarGurus. The walk scrolls and dwells there like a person, then opens detail pages with a random gap between each. It keeps going until it has visited every car the search returns that the ledger doesn't already hold.

The pacing is spread out on purpose. A search page gets four scroll steps with two to four seconds between them, then a dwell of 20 to 60 seconds. The gap between detail pages is 15 to 45 seconds, and there's a further gap of the same size before the next model and before the next site. The gap between detail pages also runs between one search's last detail page and the next search page.

Every detail tab opens as a CDP background target and closes the same way, so the browser stays out of your way on your desktop the whole time. It never comes to the front of your other windows, and the one exception is the bot-defense challenge described above.

### Known cars

A repeat walk visits only new cars. Each detail page costs about a minute, and a car the ledger already holds has nothing new to say on it except its price and whether it's still listed. Both of those are on the search page's own result card. So before the walk opens a link, it checks it against the postings the ledger already holds for that site, and it doesn't open one it already holds.

Instead, the walk touches that posting from its card. It stamps the posting as seen in this run, once the pair's walk has finished, so a pair that fails or is interrupted leaves its known postings exactly as the last completed run left them. When the card's asking price can be read and differs from the latest one on the ledger, it records the new price. The diff then works exactly as it does after a full visit. A card showing a lower price than before is listed under "Price drops", and a posting no card shows any more is listed under "Gone", because it wasn't stamped.

A touched link never enters the pool of detail visits and never spends any of `--max`. That means `--max`, when you give it, goes only to cars the ledger has never seen, and paging on Carvana goes on past pages made only of known cars until the pool of new links is full or the search runs out. What a card can't tell the walk stays as the last detail visit left it: the dealer, the Carvana shipping fee and pickup option, the fee posture, and the vehicle's year, mileage, and trim. A card price under $1,000 is treated as a misread and not a price.

`--revisit` turns all of this off and opens a detail page for every link, as the walk did before. Use it to refresh the dealer, shipping fee, pickup option, or fee posture of cars the ledger already holds, or to check a site whose cards the walk can't read yet. A posting that was dropped on its detail visit (the wrong model, a new car) never reached the ledger, so it's opened again on every walk.

### Badges

Each site prints its own opinion of a car's price as a badge on the result card, and the walk records what the card says. It reads them from the same card text it already collects for the price, so there is no extra page load. The badges are stored as posting attributes ([ledger.md](ledger.md#site-specific-facts)), which are for reading only: `odo show` lists them under the posting, and `odo rank` shows the deal badge and the dealer rating in one short field. They never touch the score ([cost-model.md](cost-model.md#site-badges-never-touch-the-score)).

A badge is a line of the card that is exactly the badge's text. A card with no badge records nothing. A posting already on the ledger has its badges refreshed when its card is touched, without a detail visit, and a new posting gets the badges of the card it was found on when its detail page is saved. A name a card doesn't show is left as it was, since a card that drops a badge doesn't prove the badge is gone.

| Site | Attribute | What the card prints |
| --- | --- | --- |
| cars.com | `deal` | Great Deal, Good Deal, Fair Deal |
| cars.com | `demand` | High Demand |
| cars.com | `dealer-rating` | the dealer's rating, a line of its own such as `4.9` |
| Autotrader | `deal` | Great Price, Good Price |
| Autotrader | `price-drop` | Price Drop |
| Autotrader | `paperwork` | Online Paperwork |
| Autotrader | `fees-included` | Dealer Fees Included |
| Autotrader | `no-accidents` | No Accidents |
| Carvana | `deal` | Great Deal |
| Carvana | `price-drop` | Price Drop |
| Carvana | `shipping` | Free shipping |
| CarGurus | `deal` | Great Deal, Good Deal, Fair Deal, High Priced, Overpriced |

A cars.com card shows a dealer rating whether or not it has a badge, so a card with a rating and no badge records the rating alone. Carvana's "Recent" tag is a sort label the page repeats, not a badge, and the walk doesn't read it. Autotrader also prints badges such as High Demand and Newly Listed that aren't recorded. CarGurus also prints "Uncertain" where it could not rate a car, which says nothing about the price and is not recorded, and `odo rank` abbreviates only the Great, Good, and Fair deals, so a High Priced or Overpriced CarGurus car shows its badge in `odo show` and nothing in `odo rank`.

### Length and the cap

The walk is uncapped by default. The scenario's own facets (model, minimum year, maximum mileage, zip and radius) are the only filter, and a pair visits every car its searches return. On a paged site (Carvana, cars.com, Autotrader) that means following it page after page until its own stop rules end it, which are the stated count being reached, a page that adds nothing new, or "No exact matches".

That's a long run. Each detail page takes about a minute once the random gaps and scroll pauses are counted, so a first walk of a whole shortlist can run to hundreds of pages and several hours. After that it only grows by the cars that are new.

You can judge the length before committing to it. The start of the run prints the pairs, the limit if there is one, and how many postings the ledger already holds for each pair. Before its first detail page, each pair prints how many pages it's about to visit and roughly how many minutes that is. Under `--max` a pair with two searches prints only the count its first search starts with. A pair with nothing new to open says so and moves on.

`--max N` puts a limit on it, and the limit is per site-and-model pair, not per run and not per raw page visit. A detail page the walk opens and then rejects for being some other model (a plain Corolla on a Corolla Hybrid walk, say), for repeating a VIN this pair already saved, for being a new-car listing, for saying the car has sold, or for listing no price never spends any of the cap. So the walk keeps taking links until the cap is met with real matches or the search page runs out of links to try.

With `--max`, each site's candidate pool is sized to twice the limit, so a wrong-model or repeat page can be replaced by a spare link instead of spending the cap outright. Without it, every link is visited and there's nothing to replace.

### When a pair fails

A pair's own coverage is only stamped on the run once that pair's walk actually finishes. A pair that errors (a page that never loads, a site that fails outright) is reported inline, and the walk moves on to the next pair rather than aborting the whole run. A walk that's interrupted partway through (Ctrl-C, a crash) leaves the pairs that already finished marked covered and the rest untouched.

### The pair line and the end table

After each pair's walk finishes, it prints one line summarizing that pair. The line gives how many detail pages were visited, how many known links were kept current from their search cards without a visit, how many were saved, and how many were dropped. The dropped count is broken out by reason when it's non-zero: wrong model, new-car listing, listing sold, no price listed, missing fields, no VIN, repeat, failed to load, and extraction failed. When that line would be wider than the console, the breakdown moves intact to a second line indented by four spaces, and it never wraps mid-parenthetical. A pair still reports as one row, however many searches or result pages it took.

At the end, a summary table lists the same figures for every pair, with a "Known" column beside "Pages" and "Saved" for the known count. The usual diff for the whole run follows the table, using the five headings described in [commands.md](commands.md#what-search-asks-for).

### The Gone reasons

Every row under "Gone" ends with a short reason, so a car the walk simply no longer looks for isn't mistaken for one that sold. The reasons are checked in this order:

- "sold" when this run opened the posting's detail page and it said the car has sold (see "Sold and no-price pages" below).
- "below year facet" when the vehicle's year is under the scenario's minimum for its model.
- "over mileage" when its mileage is over the scenario's maximum.
- "search moved" when this run's zip or radius differs from those of the run that last saw the posting.
- "card never rendered" when this run's render wait gave up on this exact posting's own search card while the ledger already held it (see [cars.com](#carscom) above).
- "pages unread" when a result page after the first failed to load, so the walk never read the pages after it (see below).
- "beyond the cap" when an explicit `--max` stopped the pair before the site ran out of results (see below).
- "not on search page" otherwise.

"Sold" is the one reason the site itself confirmed. Of the rest, only the last suggests the car may have left the market. When a pair has both reasons (a cap on one of its searches and a failed page on another), "pages unread" wins. "Card never rendered" is its own case: it is checked per posting rather than per pair, so it wins over "beyond the cap" or "pages unread" too when a pair happens to also be capped or have a failed page. A run recorded before the ledger kept its zip and radius is never treated as a moved search.

A pair is capped when `--max` kept the walk from reading everything the site returned. That happens when the pool of links filled while a paged site had more pages, or when a second search was never opened because the cap was spent. With `--revisit`, where the pool also holds links the ledger already knows, a link the pool had no room for or the cap left unvisited caps the pair too. Without `--revisit` a leftover link is one the ledger does not hold, and every known posting on the pages that were read has already been kept current from its card, so leftovers alone never cap a pair. A pair whose pages were exhausted is not capped, even when it filled the cap exactly, whenever the site states its match count. A Carvana page that shows none and fills the pool on its last page is still treated as capped, since only loading one more page would tell. A CarMax search is also capped when its show-more presses stop before the page holds as many cards as the count states, beyond a small tolerance (see [CarMax](#carmax)), since the cards past those were never read.

A capped pair still counts as covered, so a car it did reach is kept current as usual. It is also stamped as partial coverage, with a `capped:` token beside its `source:model` one in the run's sources. A posting of that pair the run did not touch is listed as "beyond the cap" rather than "not on search page", because the walk never looked for it and nothing says it sold. A later run that covers the pair in full compares against the newest run that covered it in full, so a posting a capped run never reached is still reported (as "not on search page" if it is still missing) rather than dropping out of the comparison. When any rows are beyond the cap, the heading says how many, for example "Gone (33, 20 beyond the cap)". The pair's own summary line ends with ", capped", and its Status in the end-of-run table reads "capped".

A pair whose later result page failed to load is treated the same way, with a marker of its own: an `unread:` token beside its `source:model` one. Its untouched postings are listed as "pages unread", the heading counts them beside the beyond-the-cap rows (for example "Gone (33, 20 beyond the cap, 5 pages unread)"), its summary line ends with ", page N failed" (N being the first result page that failed), and its Status in the end-of-run table reads "unread". A later run that covers the pair in full compares against the newest run that covered it in full, exactly as it does after a capped run. Re-running the walk reads the pages again.

A known posting whose card never rendered is not treated this way: it gets no marker beside the pair's `source:model` token, so the pair's own coverage still reads as full whenever nothing else capped it, and a later run compares every other untouched posting in the pair against this run rather than freezing at whichever run last completed it. Only that one posting is exempted, in the ledger itself rather than on the run: its stamp lets `odo rank`, `odo show`, and `odo research` keep listing it exactly as they would a posting "beyond the cap", even once a later run's full coverage would otherwise have dropped it (see [ledger.md](ledger.md#how-a-run-stamps-lastseen)). The heading counts these rows beside the beyond-the-cap and pages-unread ones too (for example "Gone (33, 20 beyond the cap, 1 card never rendered)"), but the pair's own summary line and its Status in the end-of-run table are unaffected: neither says "capped" for this reason alone.

## Rules every site shares

Every site's search URL carries the scenario's minimum model year and maximum mileage as facets. That way the per-pair cap is spent only on cars the scenario can rank, and not on ones the walk would then drop as below the minimum year or over the mileage limit. Both values come from the scenario. The minimum year is per model, and `minModelYearOverrides` wins over `minModelYear`, so the shipped scenario's Camry Hybrid searches from 2018 and every other model from 2019. The maximum mileage comes from `maxMileage`. Changing the scenario changes the search with no code edit.

Not every site actually honors its own URL's year range and mileage cap (see [CarMax](#carmax)), so for a site whose card states its year and mileage, both are checked again at link collection, against the same floor and cap, before the card is ever a candidate. A card whose title line states a model year under the floor is skipped before it ever enters the pool of detail-visit candidates, and so is one whose mileage line states a figure over the cap; a card whose text states neither is kept as it always was. For a hybrid-only-from-year model, a card titled with the base model alone (no "Hybrid" in it) is held to whichever of the scenario's own floor and the hybrid-only year is later, since such a card can only ever be a real candidate at or after the cutover: a "2020 Toyota Camry" card on a Camry Hybrid search (hybrid-only from 2025) is skipped even though 2020 is at or above the scenario's own 2018 floor, the same reason a page reading that way is dropped as gas-only-before-year once actually visited. The pair line adds a "below year floor" count and an "over mileage cap" count, each only when that count is itself non-zero, apart from the beyond-radius and no-distance counts, for example "10 below year floor, 2 over mileage cap". A known posting skipped this way is still touched from its card, the same as one that passes the floor and cap: its LastSeen moves with this run, so declining to spend a detail visit on it never later reads, in the diff, as the car having left the market.

The scenario's own price ceiling (`filters.maxPrice`, see [scenario.md](scenario.md#filters)) is checked the same way, but on every site, not only one with a year and mileage facet: a card whose own stated price, plus any shipping or delivery fee that same card states, already comes to more than `maxPrice` is skipped before it ever enters the pool, so a car Brian would never buy costs no page visits. CarGurus's card price already has its shipping fee inside it ("Price includes $462 shipping"), so that fee is never added a second time there; every other site's card fee, when it states one, is added to the card's own price. A card whose text states no price at all is kept, the same as one stating neither year nor mileage, since an unread price is never mistaken for one over the ceiling. The pair line adds an "over price ceiling" count, apart from the below-year-floor and over-mileage-cap counts, for example "298 over price ceiling", and a known posting skipped this way is touched from its card exactly like one skipped for its year or mileage: its price is refreshed from the card and its LastSeen moves, so it is never reported gone for want of a visit this walk was never going to spend on it. A scenario with no `maxPrice` set skips this check entirely, and the pair line's count stays at zero. No site's search URL carries a price facet: CarMax's own year and mileage facets already turned out not to bound its results (see [CarMax](#carmax)), so an unverified price facet is trusted no further, and no other site's has been checked against a live page either. `maxPrice` is enforced only by this per-card check, which needs no site cooperation at all.

A card that merely shows no price the walk can read is different from one that states outright it has none. CarGurus's own cards sometimes do the latter, a "No Price Listed" line of its own, and such a card can still name a shipping amount right above it ("Price includes $1,498 shipping", recorded card for JTDADABU0T3033887): that amount is what the delivery costs, never the car, and is never read as the price either way. Checked ahead of the price ceiling (and whether or not the scenario even sets one), this card is skipped before it ever enters the pool, the same as one over the ceiling, with a known posting behind it touched current from its card the same way. The pair line adds a "no price stated" count for it, apart from the over-price-ceiling count, for example "2 no price stated". Before this, such a card was kept, visited, and only then dropped as missing its price after spending a detail page's worth of the pair's cap and pacing for nothing.

Every detail page is checked against the model its pair is walking. A page for some other model is dropped as "wrong model". Since the search URLs now filter to the exact requested model in the common case, this check is a safety net and not the way the walk narrows down to real candidates.

Before that check runs, a page whose extraction left the model blank gets one more chance: the walk reads it off the page's own title line instead, the text between the make and the extraction's own trim on the first line that opens with the year and make asked for (a "2026 Toyota Camry SE Sedan 4D" title, with trim "SE", yields "Camry"). Every site gets this fallback, not only the one it was first built for (CarMax): Carvana and CarMax both print the trim on the line below the title rather than beside the model, so the whole remainder of that line is the model there whether or not a trim is given. A title whose first year-and-make line names some other year or make, or that names nothing after the make at all, leaves the model blank, and the page is then checked, and if need be dropped, on that blank model like any other.

A walked page counts as a hybrid model's match when the extraction names the hybrid. It also counts when the page's own title line reads `<year> <make> <base model> Hybrid` (for example "2023 Toyota Corolla Hybrid"), even though the extraction split it into a base model and a trim. A third route is a fuel spec line in the page's own spec block that says hybrid. Autotrader titles its pre-2025 Corolla Hybrids and Camry Hybrids like the gas cars ("Certified 2026 Toyota Corolla SE FWD") and says so only in the spec block. So the walk accepts a line that starts with "Hybrid: Gas/Electric", "Fuel Type: Hybrid", "Fuel: Hybrid", or "Engine: ... Hybrid" (in any letter case), provided the extracted make and base model match and the line sits above any similar-vehicles or recommended-cars heading. A fourth route is the extraction's own fuel type reading "Hybrid" for a page whose make and base model otherwise match, even when the title, trim, and spec text never say the word at all: a Carvana page the extraction reads as "2026 Toyota Camry SE, fuel type Hybrid" matches this way, since Carvana's own fuel-type search facet already confirmed the car is a real hybrid.

Only the title line, that spec line, and the extraction's own fuel type decide it. A plain Corolla page that merely mentions a Corolla Hybrid elsewhere, or whose padded similar-vehicles cards carry a hybrid spec line, is still dropped as the wrong model, and the saved candidate carries the walked model either way. The drop line for a hybrid query says what was checked ("no Hybrid in title, trim, or spec line"), except when the extraction's own fuel type said Hybrid, since the page would then be accusing its own reading of lying about itself; that phrase is left off in that case. A page whose model is blank even after the title-line fallback gets a plainer drop line instead, "model missing from extraction", since there is nothing meaningful left to compare against the model this pair is walking.

The hybrid-only-from-year rule feeds the same check. When the scenario's `hybridOnlyFromModelYear` says a base model has no gas version left, a page at or above that year matches the hybrid model even if it never says "Hybrid", and [scenario.md](scenario.md#per-model-maps) covers the field itself. Below that year the page has to say "Hybrid" like any other, and the drop line for a gas page names the year it's gas-only before. This rule is also why cars.com and CarGurus get a second search for such a model.

The Toyota Prius pair's own searches mix in the Prius Prime, Toyota's plug-in hybrid variant, the same way a hybrid pair's search mixes in gas trims, but the Prime is not a candidate: Brian ruled it out (reversing an earlier ruling), so a page reached through that pair is read as a Prime, rather than checked against the plain "Toyota Prius" query, when its own extracted model names "Prime" (a title reading "2021 Toyota Prius Prime Limited"), when its extracted model instead names "Plug-in Hybrid" (Toyota's own name for the car from model year 2025 on, in any spelling of "in", with a hyphen ("Prius Plug-in Hybrid") or without ("Prius Plug In Hybrid"), for a title such as "2026 Toyota Prius Plug-in Hybrid SE" that names no "Prime" at all), or when its extracted fuel type reads "Plug-in Hybrid" (again either spelling of "in") for a page whose model names neither, and its make and model still say Toyota and Prius, so a stray page for some other Toyota plug-in hybrid is never caught by this. A brand-new such page (the ledger has never seen it before) is dropped with the reason "Prius Prime, not a candidate", the same as a wrong-model drop never spending the pair's cap, and it is never saved. A page that is a plain Prius (no "Prime" or "Plug-in Hybrid" wording anywhere in its model, and a fuel type that isn't "Plug-in Hybrid" either) is unaffected. The walk doesn't run a separate pair search for Prius Prime on any site, and never will while it stays excluded: it's recognized only through the Prius pair's own searches, to drop it. The Prius pair's own run coverage token still gets a "site:Prius Prime" token stamped beside its "site:Prius" one whenever its own search runs (with the same partial-coverage markers as the pair's own, when it has any): this is unrelated to whether the Prime is a candidate, it's what lets a Prime row already on the ledger (see below) be reported gone the same as any other vehicle if the pair's search ever stops finding it, instead of pricing a stale posting forever.

A Prime row already on the ledger, stored as a plain Prius before this ruling, is the one case a Prime page is still saved rather than dropped: run `odo walk <site> --model "Toyota Prius" --revisit` per site (cars.com, carvana, autotrader, carmax, cargurus) to open its known Prius detail pages again, and a page that now reads as a Prime relabels the row to Prius Prime, the ordinary way any sighting updates a vehicle's fields, rather than dropping it. That relabel is what lets the row exclude by name (see [scenario.md](scenario.md#filters)) instead of continuing to pass as a plain Prius; nothing is ever deleted from the ledger for this. Nothing guesses this from a VIN alone, only a revisited page.

cars.com's used search still mixes in new-car cards ("New 2027 Toyota Corolla Hybrid LE"), which the scenario can never rank. So the walk skips any card whose title begins with "New " when it collects detail links, and those links never enter the candidate pool and never count against the cap. As a backstop, a cars.com detail page that still reads as a new car is dropped as a "new-car listing", which likewise never spends the cap. A page reads as a new car when it has a "New" title before the year, or when it has an MSRP line with no Mileage line. "Missing fields" stays as the reason for a used car whose page lacks its year, price, or mileage.

### Sold and no-price pages

Two kinds of detail page are recognized from their text before extraction is attempted, so the drop reason says what actually happened and no extraction call is spent on them. A page that says the car has sold is dropped as "listing sold". A page that lists no price, only a prompt to contact the dealer, is dropped as "no price listed". Neither spends any of the per-pair cap, and both are named in the pair line and the end table.

A sold page carries other cars' cards, so the extraction would otherwise read one of those and drop the page as "no VIN". When the link is already a posting on the ledger, which happens under `--revisit`, the walk stamps that posting as sold for this run. The posting is not touched otherwise, so the diff lists it under "Gone" with the reason "sold". A sold page for a link the ledger never held marks nothing. A page with no price never creates or updates a price observation, since the car is still for sale and only its price is unknown.

Each site carries its own patterns for the two pages, and a site without them drops such a page for whatever the extraction makes of it. Only Autotrader has them so far: its sold page says "It looks like this Toyota Corolla has already found a new home", and its no-price page prints "Contact Dealer For Price" on a line of its own in the page header (the dealer's other cars, listed further down, are not read, since an unpriced one prints the same prompt on a page whose own car is priced). The cars.com and Carvana wording is added once a page saying so has been recorded.

## Per site

### cars.com

cars.com's model facet lowercases the model name and collapses every run of non-alphanumeric characters to a single underscore, after the make and a hyphen. "Toyota Corolla Hybrid" becomes `models[]=toyota-corolla_hybrid`, and "Honda CR-V Hybrid" becomes `models[]=honda-cr_v_hybrid`. That way the search URL isolates the hybrid model directly. The scenario's minimum model year and maximum mileage go in as the plain `year_min` and `mileage_max` query parameters. A cars.com result page holds about thirty cards, and the search URL carries no `page_size` parameter because the site ignores it (a live check loaded the same search with and without `page_size=100` and got the same page size either way). The walk follows `page=N` instead, as described under [Carvana](#carvana) below, and stops when a page adds no new link.

The URL's `maximum_distance` doesn't actually bound what the site hands back: a padded later page keeps returning cars far outside it, and some cards state no distance at all. So every card's own stated distance is checked at link collection, against the scenario's radius, before the card is ever a candidate. An ordinary card states it as "`<City>, <ST> (N mi)`" ("Sanford, FL (28 mi)"), and a CarMax listing carried on a cars.com card states it the same way after its delivery fee ("$249 delivery to Orlando, FL (14 mi)"); either is measured by that N, at or under the radius kept and over it skipped before it ever enters the pool or is checked against the ledger. A card whose text is empty or otherwise states no distance at all (the site's own nationwide recommendation links, which pad a later page the same way, and an ordinary card's own photo link, both of which can land the page's nearest-dollar-ancestor bounding on a wrapper spanning several neighboring cards instead of the link's own), or states more than one distance (that same wrapper case), is skipped too, but counted apart from a beyond-radius card so the two never blur together. The pair line reports both counts when either is non-zero, for example "12 beyond radius, 2 no distance stated"; a link the pair line counted as skipped on an earlier page is withdrawn from that count the moment a later page instead pools it or resolves it against the ledger from its own in-radius text, so a car the walk kept is never left counted as skipped. Because neither kind of card ever adds anything to the pool, a page made up of nothing but them, or of links this pool already holds, ends the paging exactly as an empty page does.

Before it reads a page's cards at all, the walk waits for each one to render its own price. cars.com hydrates each card's own `fuse-card` element after the page loads, and a card still empty at that moment is a rendering delay, not the site's own nationwide recommendation link described above: an ordinary in-radius car's card can be the one still empty when the page first loads, just as readily as a nationwide link's. Read too soon, such a card leaves nothing of its own for the card-text pull to stop at, so the walk used to climb past it and read a neighboring card's whole wrapper text as this card's, which the radius check reads as stating more than one distance and so as stating none, wrongly skipping a car it never actually measured (two in-radius Honda Insights, Driver's Mart Sanford at 28 mi and Toyota of Melbourne at 39 mi, would be skipped this way from a page that hadn't finished rendering). So before link collection reads a page, it scrolls a still-empty card into view (to trigger the render) and rescans, up to a bounded number of times, ending as soon as every card has rendered. A card still empty when that bounded wait gives up is neither pooled nor touched from its card; it's counted apart from the beyond-radius and no-distance counts, for example "1 unrendered", and its href is written to the run's recording (see [Recorded pages](#recorded-pages)) so a later look can tell which car the page never rendered in time. cars.com's padded later pages can repeat the same car, so a card counted unrendered on one page but read normally on another (pooled, or counted beyond radius or no distance) is not counted unrendered at all. But a card that stays unrendered on every page it appears on is never touched from the ledger's side either, even when the ledger already holds it: its card was never actually read, so touching it would keep it current for rank without ever measuring it, and would double-count it as both known from cards and unrendered. When that untouched card is one the ledger already holds, it is exempted from the diff on its own rather than marking the whole pair's coverage partial: the pair still reads as fully covered as long as nothing else capped it, and this one posting alone is reported gone under "card never rendered" (see [the Gone reasons](#the-gone-reasons)) rather than folding it into every other untouched posting's reason; its href is in that page's recording (see [Recorded pages](#recorded-pages)) either way.

A model the scenario marks hybrid-only from some year on is searched twice. A base model that went hybrid-only is filed under its own base-model bucket for the years after the cutover, rather than the separate hybrid one, while the years before it stay under the hybrid bucket. So the walk issues one search for the hybrid facet (`models[]=toyota-camry_hybrid`) from the scenario's minimum year. It then issues a second for the base-model facet (`models[]=toyota-camry`) from the hybrid-only year itself, or the scenario's minimum year if that's later, and it visits them in that order.

The two facets can't share one URL, because cars.com takes a single `year_min` per request. A combined search would have to start the base model at the scenario's minimum year too, which is 2018 for the Camry Hybrid. It would then fill up with gas Camrys from 2018 through 2024, which the walk rejects as the wrong model after the cap is spent on them.

With no `--max` there's nothing to share out. Both searches are loaded first, with a random gap between them, and a link both carry is kept once. Every link is then visited, so the pair's page count is known before its first detail page.

With `--max`, each search starts with an even share of the cap, and the odd page goes to the hybrid-facet search. Each search gets its own link pool of twice its share, and a share a search can't spend because its page runs out of candidates rolls forward to the next search. If the first search still has links it never visited when the second is done, the cap that's left goes to those. So the pair falls short of `--max` only when both searches are exhausted, and it never saves more than `--max` in total.

The console labels each search page ("search 2 of 2") with its model facet.

cars.com is paged like Carvana (see below), so a pair with more matches than one result page holds is not truncated at its first page. Each of the two searches of a Camry pair pages on its own facets. With `--max`, the per-pair cap is unchanged and the two searches still share it exactly as described above. Of the two extra stop rules Carvana uses, cars.com uses neither yet: its page body prints no match count and no "No exact matches" marker is known for it, so its paging ends when the pool is full (only with `--max`) or a page adds no new link.

The card price on a cars.com card is the first dollar amount on it, because its price comes before a price-drop amount, the mileage, and the "Used 2023 ..." title.

### Carvana

Carvana has no separate hybrid model at all. It filters its base-model search by fuel type instead, and its `cvnaid` query parameter carries a base64url-encoded JSON filter naming the base model plus `"fuelTypes":["Hybrid"]`. The minimum model year and maximum mileage go inside that same JSON as `"year":{"min":N}` (singular, since a `"years"` key is silently ignored) and `"mileage":{"max":N}`. The URL carries the zip and no radius. Because the fuel-type filter matches those listings' actual fuel type regardless of the model name, Carvana never needs a second search.

Carvana is paged, and so is cars.com. Carvana renders about 21 cards per result page but reports far more cars for the same filters (a hundred for one Prius search). So after collecting a search page's links, the walk requests the same URL with `page=2`, `page=3`, and so on. It keeps going for as long as the candidate pool is below its size (unbounded without `--max`, twice the cap with it) and the last page showed at least one link that hadn't appeared on an earlier page, which counts a car the ledger already holds.

Two more rules keep the paging to cars the facets asked for. The first page states how many cars match ("16 cars"), and that count bounds the links the pages contribute in total, taken in page order, even when a page shows a few more results than it states. And a result page that says "No exact matches" contributes no links and ends the paging, because everything after that notice is similar vehicles (other models, or other years and mileages) that the search never asked for. The console says the search ran out of exact matches on that page.

Each page gets the same scroll and dwell as the first, is recorded as its own search text (see [Recorded pages](#recorded-pages)), and is announced on the console ("search page, page 2", or "search 2 of 2, toyota-camry facet, page 1" for a cars.com pair with two searches). Only the first page is required. If a later page fails to load, the walk prints a warning, stops paging, and goes on with the links it already has rather than failing the pair. The pages after the one that failed were never read, so the pair's coverage is recorded as partial (see [the Gone reasons](#the-gone-reasons)): its line says which page failed, and a posting the ledger holds from those pages is listed as "pages unread", not as a car that left the market. A first page that fails to load still fails the pair, and a failed pair is never stamped as covered.

A Carvana card's price is the amount after "Current price:".

Carvana ships every car to the buyer, and its detail page prints a one-time shipping fee beside the price ("Free shipping" or, for example, "$1,590 shipping", and again in the delivery block). The fee depends on the car and on the buyer's zip. The walk reads that line straight off the page text, with no model in between. "Free shipping" stores 0, "$1,590 shipping" stores 1590, and a page that shows neither stores nothing, so an unknown fee is never mistaken for free. It reads only the page's own line, ahead of the "Need it sooner?" block that lists other cars.

The page also offers pickup, in a "Pickup and Delivery" block that lists the two options one after the other: "Pickup Wednesday", "Pick it up from our Orlando location", "Orlando, FL", then "or", then "Delivery Tuesday", "Delivered to you within 3 days", "Orlando, FL", and the shipping amount. The shipping fee sits under the delivery option only, and the pickup option prints no fee. The walk reads the block from the page text the same way, with no model in between. The location is the city line under the pickup line, and the pickup fee is 0 unless a dollar amount or "Free" is printed under the pickup option before the "or". A page whose block never rendered stores no pickup fee and no location, and keeps its shipping fee from the price header, so an unread pickup is never mistaken for a free one.

The block renders lazily, only once the page has been scrolled about a third of the way down. A Carvana detail page therefore gets one screen of scrolling as every page does, and if the text still lacks "Pickup and Delivery", up to three more screens, each with its own pause, stopping as soon as the block appears. Some cars never render it, and the walk gives up on those after the last step rather than waiting.

The fee is stored on the posting as its own `ShippingFee` column, not in the price history, because it isn't part of the asking price, only of what taking the car home costs. The pickup option goes in the posting's `PickupFee` and `PickupLocation` columns. Each sighting replaces the last one's values, so a later walk that finds a different fee (or none) leaves the newer figure, and a later page whose block didn't render clears the pickup option rather than keeping an old one. Every other site stores no fee. [cost-model.md](cost-model.md#what-a-purchase-price-means) covers how each fee counts, and how the scenario's `fulfillment` chooses between them.

### Autotrader

Autotrader is the third site, and the only one of the three that lists private sellers as well as dealers, since cars.com and Carvana carry none. That also makes it where smaller dealers who don't list on cars.com turn up. Its search URL is `https://www.autotrader.com/cars-for-sale/used-cars/<make>/<base model>?zip=<zip>&searchRadius=<radius>&startYear=<minimum model year>&maxMileage=<maximum mileage>&sortBy=relevance`. The zip, radius, minimum model year, and maximum mileage all come from the scenario like every other site's facets.

There's no `sellerTypes` parameter, on purpose. Leaving it out returns dealers and private sellers together, and `sellerTypes=d` and `sellerTypes=p` narrow to one or the other.

Autotrader has no separate hybrid model. Its model slugs are the base models (`prius`, `corolla`, `camry`, `insight`), and a slug it doesn't know silently returns every listing for the make. So a hybrid variant of a base model ("Corolla Hybrid", "Camry Hybrid") searches its base model and adds `&fuelTypeGroup=HYB`, while a model that's hybrid by name ("Prius", "Insight") gets no fuel facet. A hybrid-only-from-year rule needs no second search here for the same reason it needs none on Carvana, which is that the fuel facet matches each listing's actual fuel type.

A search page states its result count ("13 Matches") and then fills the rest of the page with cards the facets never asked for. Those are other years, other models, new cars, and listings beyond the radius, and a page with no matches at all is filled with such cards entirely. So the walk reads the count first. A page reading "0 Matches" contributes no links, and a page with N matches contributes at most N listings. Those come from the cards the page marks as ordinary results (`clickType=listing`), so the sponsored card at the top, which ignores the search facets and isn't one of the N, never takes a match's place.

A detail link matches `/cars-for-sale/vehicle/<digits>`, and the walk stores it without its query string or a fragment such as `#purchaseConfidence`, so one listing is one candidate however many times a page links it.

A private seller's detail page marks the seller with a "(Private Seller)" line. The walk stores that posting with the dealer "Private seller" and no location, and not the person's name and city. Every other rule applies to it unchanged: the model check, the cap, the pacing, and the bot-challenge pause.

Autotrader is paged too, now, like cars.com and Carvana, just by a different parameter. A page holds 25 `clickType=listing` cards, and later pages are requested from the same search URL with `&firstRecord=25`, `&firstRecord=50`, and so on, an offset by record count rather than a page number: a live search fetched directly from autotrader.com on 2026-09-27 showed the same 25 cards on a first page every time, and appending `&firstRecord=25` to the identical URL returned a second page of 25 more with no listing id repeated from the first. Before this, Autotrader had no paging at all, so a search stating more matches than one page holds (a walk run recorded a 39-match search on 2026-09-27, and a 41-match one the day before) was truncated at its first 25, its stated count notwithstanding, and every posting beyond that page read as gone from a search that never actually looked for it. The stop rules are the same ones cars.com and Carvana already use: the stated count being reached, or a page adding no new link. A pair whose later page fails to load is capped the same way too, with the pages after it reported "pages unread" rather than "not on search page" (see [the Gone reasons](#the-gone-reasons)).

Autotrader's card shows the price as bare digits ("19,394"), with no dollar sign, immediately before "See payment", and an unpriced card prints "See payment" with no digits before it at all. `SearchPageLinks`' ancestor climb otherwise looks for a dollar sign followed by a digit, which neither shape has, so before this was read every real card's own dollar-ancestor test failed and its card came back empty; only a "New ... MSRP$" recommendation card and a "Consider Buying New" one, both of which do print a dollar sign, ever carried card text, and neither is ever a candidate anyway (its link carries no `clickType=listing`). Autotrader overrides that ancestor test to also accept "See payment" on its own, so the climb stops at the right card whether or not it has a price, and reads the bare-digit figure as the card's price when there is one. A known Autotrader listing is kept current from its card the same way cars.com's and Carvana's are, with no detail visit needed to see a price drop.

That first matching ancestor is only where the card's own text starts, though, not where it ends. The same live fetch on 2026-09-27 (a Corolla search, zip 32801, 50 miles) showed a real card's DOM, from the title anchor outward, is a "title-info" div (year/make/model/trim), inside an "inventory-listing-body" div that adds the price and "See payment" (the ancestor the climb used to stop at), inside an "item-card" div that adds the dealer's name, distance, phone, and "Check Availability" or "Online Paperwork", inside one more wrapping div that adds a top-of-card badge such as "Price Drop" or "Newly Listed" when the card has one. Stopping at the first match therefore missed both the badge above it and the dealer footer below it (PR #79's review found this from a recorded card whose "Price Drop" and "Online Paperwork" never reached its stored badges). One ancestor further out than that wrapping div is the results list holding every other card on the page, so Autotrader's card container is found by widening past the first match, one parent at a time, for as long as the parent's own text still carries only the one price marker the card itself accounts for, and stopping at the last parent before one carries more than one (the shared list, with a marker per card). cars.com's and Carvana's cards need none of this, since their own first matching ancestor already is the whole card.

### Fee statements

Dealers on cars.com and Autotrader can add fees to the price they list, so each detail page from those two sites is read for what it says about them. The walk reads the page text with a fixed reader (`FeeStatements`), with no model in between, and stores the answer on the posting as its fee posture and itemized total. CarGurus is read too, but from its search card and not its detail page (see [CarGurus](#cargurus)). Carvana and CarMax are not read, so their postings keep a null posture, which means "never read" and is different from `unknown`.

The question the reader answers is whether the page says the price it shows already contains the dealer's fees. That matters because the price the walk stores is normally the page's headline price. On every page recorded on 2026-09-26 that lists its fees line by line, the headline price is the printed total with those fees already inside it, so adding the itemized lines a second time would count them twice. There are three answers:

- **all-in** means the page says the fees are in the price. On cars.com that is "Seller has no extra fees" with "The price shown here is the all-in total", or a "Vehicle price breakdown" table that ends in an "All-in total price" row. On Autotrader that is "No Additional Dealer Fees", or a "Listing Price" block whose fee lines end in a "Total Price" followed by "Dealer Fees Included". A page that lists fee lines and also says they are included is all-in, and nothing is added to its price. The sum of its fee lines is still stored, so `odo show` can say how much of the price is fees.
- **itemized** means the page lists fee lines with amounts and never says they are included. The total is the sum of those lines, and it is added to the purchase price. On cars.com the lines are the rows of the breakdown table after the vehicle price. On Autotrader they are the "+ $amount" lines after the listing price. No recorded page has this shape yet, so the tests build it from a recorded page with the statement edited out.
- **unknown** means neither. That covers cars.com pages with only the generic taxes and registration disclaimer, or with "Seller has not disclosed fees", and Autotrader pages whose listing price block says nothing about fees.

Two guards keep the reader from borrowing a statement that isn't the page's own. On cars.com the all-in sentence is matched whole, because the undisclosed-fees notice tells the buyer to "confirm the all-in total price directly with the seller". On Autotrader only the page's own "Listing Price" block is read, because a search-style page that some detail links land on lists other cars, each with its own "Dealer Fees Included" badge, and has no block of its own, so it reads as unknown. On cars.com the first fee statement on the page is the listing's own, since similar listings come after it, so a later one is never read.

The price comes from the extraction model, so it is not always the headline price: in run 20260926-121057 one Autotrader page (VIN 4T1DAACK2SU548011) stored its $26,695 listing price and not its $28,193 total. When the page prints both a listing price and a total that differ by exactly its fee lines, the walk compares the stored price with them. An extracted price equal to the listing price means the fees are not in it, so the walk stores the page's total instead and the reading stays all-in. It is not turned into itemized, because a later cars.com search-card touch re-bases the stored price on the card's fee-inclusive figure and leaves the posture alone, so an itemized posture would count the fees twice. An extracted price equal to the total means they are in it, so an itemized reading becomes all-in and the fees are not counted twice. Any other stored price leaves the reading as it was.

The posture and the total are stored on the posting, and each sighting replaces the last one, the same as the shipping fee. A dealer whose page reads as unknown and who sells add-ons according to CarEdge raises the `add-ons-dealer` red flag, described in [research.md](research.md#red-flags). [cost-model.md](cost-model.md#what-a-purchase-price-means) covers how an itemized total counts.

### CarMax

CarMax is the fourth site, and the one whose stock cars.com and Autotrader mostly do not carry, since CarMax sells its own cars. It sells them at one no-haggle price, so the price on the page is the price, and it prints what taking a car home costs on each search card. Its search URL is `https://www.carmax.com/cars/<make>/<model path>/<minimum model year>-<current year + 1>?zip=<zip>&distance=nationwide&mileage=<maximum mileage>`. The model path is the base model, followed by `/hybrid` for a hybrid variant of a base model, so the scenario's models search `prius`, `corolla/hybrid`, `camry/hybrid`, and `insight`. The site redirects `corolla-hybrid` to `corolla/hybrid`, so the walk builds the slash form directly. The year range runs one past the current year because a dealer stocks next year's model year before the year turns. The zip and maximum mileage come from the scenario like every other site's facets. A model with a hybrid-only-from-year rule still gets one search here. CarMax's `/hybrid` path does reach a base model's post-cutover hybrids: the recorded 2026-09-27 Camry Hybrid search's own cards include 2025 and 2026 cars titled just "Camry", with no "Hybrid" in the title at all.

The search URL's own year range is not actually honored, though: that same recorded search, whose URL started at the scenario's 2018 floor, still returned ten cards below it (2014 x3, 2015 x2, 2016 x3, 2017 x2). So a card's own stated year and mileage are checked again at link collection, the same way as [every site shares](#rules-every-site-shares) above, before either is ever a candidate; without this, the walk would spend a detail visit on each below-floor car the first time its search page lists it, and again on every newly listed below-floor car after that, since nothing else in the walk itself re-checks them once the search hands them back. A below-floor car the ledger already holds is not visited again either way, once known from an earlier walk, with or without this check: this check is what keeps a below-floor car from ever earning that first visit at all.

CarMax ignores the scenario's radius on purpose. The search always says `distance=nationwide`, which is a per-site override and not a bug. CarMax moves a car from any of its stores to the buyer for a fee printed on the card (as little as $49), so a car far away is a real candidate here, and a radius would hide most of the stock. The recorded Prius search matched 526 cars nationwide and 4 within the default radius. The run still records the scenario's radius for the search-moved check (see [The Gone reasons](#the-gone-reasons)), so changing the scenario's radius alone does not change what a CarMax walk searches.

A search page prints two kinds of "N matches" lines. The first is the filtered count for this search ("526 matches"), and further down the page prints site-wide and category totals ("86,317 matches"). The walk reads the first line only, and never a later one. The "Show 25 matches" button is not a count either, so a line starting with "Show" is skipped. The count bounds the links the page contributes, as on Autotrader.

CarMax pages its cards behind that button and not by URL. After the usual scroll and dwell, the walk presses the show-more control until the page holds as many cards as the count states or a press adds nothing new. The recorded Prius page labels that control "Show 25 matches", and the live Camry Hybrid page of 2026-09-26 labels it "Load more", so the walk presses either one. The live page also prints an "N of M results" line above the control ("44 of 527 results"), which is progress and not the count: the stated count is still the "527 matches" line at the top of the page, and the results line is never pressed or read as a count. A press that adds nothing gets one more pause and a second look before it ends the run, since the cards arrive a moment after the click, and a search never gets more than 200 presses. Each press is paced like a scroll step and stops for a bot-defense challenge if one appears. The console reports how many cards were loaded and how many presses it took, and the recorded search text and cards file are written after the last press. The site's count can run a card or two past what it will render (a walk on 2026-09-26 loaded 521 cards against 522 stated), so a run that ends because a press added nothing, with the cards within a small tolerance of the stated count (two cards, or one percent of the count, whichever is larger), is treated as complete, and the console says the count was within tolerance. If the presses stop with fewer cards than that (the control was covered and could not be clicked, a press added nothing with a larger shortfall, or the press limit was reached), the console says so and the pair is stamped as partial coverage, so the known cars further down the list read as "beyond the cap" and not as gone.

A detail link matches `https://www.carmax.com/car/<digits>`, where the digits are a stock number and not a VIN. The walk stores it without its query string.

The fee comes from the card, since the card is where CarMax prints it for every car. A card that reads "$49 shipping·Get it by Monday" (or "$149 shipping·Get it by Sep 28 - Oct 2") stores a `ShippingFee` of 49 (or 149). A card that reads "Available today·Orlando" is a car at a nearby store, so it stores a `ShippingFee` of 0 and a `PickupLocation` of Orlando. A card with neither line stores nothing, so an unknown fee is never mistaken for free. Both are replaced on each sighting, so a car that moves from a store to a transfer loses its pickup city. The walk finds each car's card on the search page it opened the detail page from, so a listing's fee is the one its search card showed. A known car touched from its card gets the card's fee too, since the card is where CarMax prints it and the fee moves with the car (a car at a store one week can be a transfer the next), so a later walk's card replaces the stored fee and pickup city without a detail visit. A known car's card that prints neither line leaves the stored fee alone. [cost-model.md](cost-model.md#what-a-purchase-price-means) covers how the fee counts.

The detail page's visible text does not print the VIN, but its HTML does. So the walk reads the VIN from the HTML, as the value under a `vin` or `vehicleIdentificationNumber` key (the recorded car/29085801 page carries JTDACACU8S3046841 that way), and reads the rest of the fields (price, mileage, year, and model) from the text through the extraction as on the other sites. The model has a fallback: the extraction is checked against the page text, and a model the page does not print (the extraction writing "Camry Hybrid" for a page titled "2025 Toyota Camry") is dropped, which used to leave the page rejected as a wrong model. When the model comes back blank, the walk reads it off the page's own title line instead (see [Rules every site shares](#rules-every-site-shares)), the text after the year and make on the first line that starts with a year ("Camry", since CarMax's title line carries no trim to bound it against), so a 2025 Camry still counts as the Camry Hybrid under the scenario's hybrid-only-from rule. The dealer is not one of them. CarMax is many stores under one name, and the extraction is asked for the selling dealer and not the site's name, so it tends to return none for a page full of "CarMax". The walk reads the store with a fixed reader (`CarMaxStores`) instead, from the first line of the page that opens with one of six shapes: "Test drive at CarMax Orlando, FL" (a car at a nearby store), "Ships from CarMax Clearwater, FL" (a car that has to be moved), "Available at CarMax Orlando" or "Only at CarMax Laurel, MD" (a car already on a lot), "Reserved at CarMax North Houston, TX" (a car held for another buyer), or "Coming to CarMax Mobile, AL" (a car still in transit). A store's own name can carry a slash between two cities that share one store ("Arlington/Ft. Worth") or a parenthetical ("Jackson (MS)", "Boise (Meridian)"), and the reader keeps that whole name. The dealer is the full store name ("CarMax Orlando") and its location is the city, with the state when the line prints one ("Orlando, FL"). Only the first such line counts, since the similar cars listed further down name other stores. A known posting stored under the bare "CarMax" moves to its store the next time its detail page is read. A page whose HTML gives no VIN is recorded whole as `detail-N.html` beside its text, so the reader can be fixed against a real page. A page whose header matches none of the six shapes is still stored with the dealer "CarMax" and no location, the same as a page that names no store at all, but the walk's own console line for that page says the store line was not recognised, so an operator seeing many of them knows a new header shape has shown up. A "Reserved at" header also stores a posting attribute saying the car is reserved for another buyer, and a "Coming to" header one saying it is in transit and not yet purchasable; `odo show` lists either beside the posting the same as any other attribute, and `odo rank` shows it on its own line under the row, in red. Unlike a card badge, this attribute does not survive a later sighting that leaves it unmentioned: any other recognised header shape clears it outright, so a car that arrives or has its hold released loses the note the next time `--revisit` reads its detail page. A vehicle with another live posting that isn't reserved or in transit and has a valid price still ranks with the note shown, priced from that other posting; one whose only live postings all carry it, or whose only other live postings have no valid price, is excluded from `odo rank`'s ranked list instead, under the same Excluded section an over-ceiling price or every posting gone lands in (see [scenario.md](scenario.md#filters)), and starts ranking again on its own the next time `--revisit` finds the reservation lifted. CarMax states a car's mileage only rounded to thousands ("38K miles"), so the prompt tells the model to write it out in full (38000), and the check against the page text accepts a mileage within the rounding of a "NNK miles" figure (37,500 to 38,499 for "38K miles"). Mileage is the only field that gets this allowance, and only for a K directly followed by miles, so a "$38K" price on the page grounds nothing.

The card is also where the asking price is read: the first dollar amount on it that isn't the shipping fee or the monthly payment estimate. On an older card the price sits right after the title, ahead of the fee line ("$24,998\n$49 shipping..."); on a newer one it sits at the very end, after the fee line and the "Est. $.../mo" estimate ("$499 shipping...\nEst. $311/mo\n·\n$19,998"). Either way the price is the first amount left once the shipping fee and the monthly estimate are ruled out, since a price-drop card prints its current, lower price before the old one it dropped from. A known CarMax listing is kept current from its card, price included, exactly as any other site's is.

### CarGurus

CarGurus is the fifth site. It is a marketplace of dealers' cars, and it is the one whose inventory the other four miss the most: with the same facets applied, a measurement on 2026-09-26 found that of 78 cars sampled from its first result pages, 43 were not on the ledger yet (17 of 21 Honda Insights, and 15 of 20 Camry Hybrids, which the other sites' per-pair cap inflates). It also prints, on every card, what its price includes, which is why the walk reads the card and not the detail page for the figures below.

Its search URL is `https://www.cargurus.com/search?zip=<zip>&distance=<radius>&makeModelTrimPaths=m<make>%2Cm<make>%2Fd<model>&startYear=<minimum model year>&maxMileage=<maximum mileage>&sortDirection=ASC&sortType=BEST_MATCH`. The zip, radius, year, and mileage come from the scenario like every other site's facets. The year parameter is `startYear`: the site ignores `minYear`, `minModelYear`, and `yearMin`, which return every year without complaint, and it prints the years it applied as a chip ("2019 - 2026") when it honors them. The make and the model are ids that CarGurus assigns and nothing derives from a name, so they are held in one table, `CarGurusSearch`, keyed by the scenario's "Make Model" (Toyota is `m7`, Honda `m6`; Prius is `d15`, Corolla Hybrid `d2840`, Camry Hybrid `d2908`, plain Camry `d292`, and Insight `d591`). A scenario model with no row there stops that pair with an error naming the model, and the walk goes on to the next pair. The way to add one is to search for the model on CarGurus in a browser and read the two ids off the `makeModelTrimPaths` parameter of the resulting URL.

A model with a hybrid-only-from-year rule gets two searches here, the same reason cars.com's builder returns two (see [cars.com](#carscom)): CarGurus files such a model's post-cutover years under its plain base model's own id rather than the hybrid one it otherwise uses. The 2025+ Camry Hybrid is a case in point: it sits under whatever id the site's own "Camry" facet resolves to, not the "Camry Hybrid" one, and the recorded 20260928-010506 walk run's Camry Hybrid search (model id `d2908`) came back with 49 vehicles found, years 2018 to 2024 only, none 2025 or later, for exactly that reason. The base Camry's id, `d292`, was read off a live page rather than guessed: loading the Camry Hybrid search in a probe browser (a second CDP connection on port 9223 with its own `edge-probe-profile`, kept apart from the walk's own port 9222 and profile) and inspecting its embedded facet data found the sibling entry `{"label":"Camry","value":"m7/d292"}`; loading `m7/d292` directly with `startYear=2025` then showed the site's own applied-years chip as "2025 - 2026" and 394 vehicles found, confirming it. So for such a model the walk issues one search for the hybrid model id from the scenario's minimum year, then a second for the base model id from the hybrid-only year itself (or the scenario's minimum year if that's later), sharing the pair's cap exactly as cars.com's two searches do (see [cars.com](#carscom) and [Rules every site shares](#rules-every-site-shares)): cards from both are deduplicated by canonical URL, and each search stops paging by the same rules as any other paged site's search: its own stated count reached, or a page adding nothing new (see [Length and the cap](#length-and-the-cap)). The pair's own console line then names each search's own stated count beside what it actually collected ("Camry Hybrid 49 of 49 stated; Camry from 2025 18 of 394 stated"), and the pair's coverage is full only once every search has covered its own stated count within the same tolerance a stated count already allows elsewhere (see [CarMax](#carmax)); a search that falls short of it outside that tolerance marks the pair partial the same way a failed later page does, so a known posting it never reached reads as pages unread rather than gone.

A search page prints "N vehicles found", and that count is of the ordinary results only. The page also carries sponsored cards, whose links carry `sponsoredType=PRIORITY` (a dealer's ad, labelled "Sponsored by ..."), `FEATURED` (a promoted copy of a listing, labelled "Sponsored Listing"), or `HIGHLIGHT` (the same dealer's ad again on later pages), where an ordinary result's link says `sponsoredType=NONE`. A sponsored card ignores the search's facets and is not one of the counted results, so the walk never takes one as a candidate. Only that link is set aside, so a listing that is promoted on one card and an ordinary result on another is still collected through the ordinary one, and a listing promoted on this page whose ordinary card is on a later page is collected there. A detail link matches `https://www.cargurus.com/details/<digits>` and is stored without its query string, which carries the search's own session ids.

The site pages by number, about twenty cards a page, and the walk follows the pages until the count is covered or a page adds nothing new. A plain `page=N` is not enough, though. The first page holds fewer cards than the rest (18 of 21 on the recorded Corolla Hybrid search, once the ads are counted out), and a later page fetched without saying so is cut from a different offset: on that 96-car search, plain `page=2`, `page=3`, and `page=4` URLs held only 78 distinct cars between the five pages, repeated some and skipped others, and `page=5` sent the browser back to page 1. The first page's own data carries the value that lines the rest up, a short base64 string named `pageAlignment` (the two counts, `{"firstPage":18,"pageN":21}`), and the site's own page buttons put it on the URL. So the walk reads it from the first page's HTML and adds `&page=N&pageAlignment=<value>` to every later page, which gave exactly the 96 cars the page stated on the Corolla Hybrid search and exactly the 67 on the Prius one. A page past the last one comes back as the last page again, which adds nothing and ends the paging.

The card is where the figures are read, because a card and a detail page do not show the same price. A card shows what the buyer pays delivered. A detail page's headline repeats that same delivered price (nine of the ten pages of the 2026-09-26 live walk did, and the tenth was a dollar higher), but a store-transfer page also prints a breakdown that lists the dealer's price at its lot: on a store-transfer Insight the card read $27,697 with "Price includes $699 shipping", and its detail page headlined $27,697 and then listed "Dealer's price" $26,998, "Transfer fee" $699, and "Total" $27,697. The extraction can read either figure off such a page, so the posting's price is the card's (on a price-drop card, which prints the old price and then the current one on lines of their own, the current one, the last dollar-only line), and a link whose card shows no price is dropped as missing a price and is never stored at its lot price. A card that states plainly it has none ("No Price Listed") never gets that far, though: it is skipped at link collection instead (see [Rules every site shares](#rules-every-site-shares)), so it spends no detail visit finding out the same thing the slow way, and its own delivery line ("Price includes $1,498 shipping") is never read as if it were the price it says it doesn't have. A known car's card, touched without a detail visit, moves the stored price the same way.

Each card also carries fee facts:

- A card that prints "Price includes fees", or "No additional dealer fees" (which every store-transfer card on the recorded pages prints), stores a fee posture of `all-in`. A card that prints "Price includes $462 shipping" (under "Home delivery from ..." or "Store transfer to ...") is `all-in` as well, and it stores 462 as the posting's `ShippingFee`. A card that prints "Free home delivery" stores a `ShippingFee` of 0. A card that says none of these stores `unknown`, and a card with no delivery line at all (a car at a nearby dealer) stores no shipping fee.
- The shipping fee is inside the price, so the cost model shows it and never adds it. `odo show` prints it as "Shipping fee $462 (already in the asking price)", and the purchase price stays the asking price. Any all-in posting's shipping fee is treated this way; the only all-in posting that has one is CarGurus's.
- These are CarGurus's own statements, and the detail page can disagree with them. The recorded Sanford Insight card said "Price includes fees" while the dealer's own disclaimer on its detail page said the advertised price excludes a $999 document fee and a $399.87 filing fee. The walk records what the card says and never reads the disclaimer, so an `all-in` CarGurus posting is a claim by CarGurus and not a check of the dealer.
- A known car's card replaces the stored posture and shipping fee without a detail visit. A card that names none of the three fee statements, and one that prints no shipping line, leaves the stored posture and shipping fee alone, so a card that merely omits a line never erases what an earlier card said.

The deal badge is a line of the card that is exactly one of Great Deal, Good Deal, Fair Deal, High Priced, or Overpriced, stored as the `deal` attribute in CarGurus's own words (see [Badges](#badges)).

The detail page's visible text prints the VIN ("VIN:" and the number on the next line), so the walk needs no HTML reader for it. The year, mileage, and model come from the extraction as on the other sites, but the dealer name and location are read from the page's own text directly (`CarGurusDealer`), ahead of the extraction, the same way CarMax's own store is (see [CarMax](#carmax)): CarGurus has no fallback dealer, so a page the extraction misreads would otherwise store a wrong hub rather than nothing.

The name is the first line under the page's own "Dealer" heading that isn't one of that heading's own badge lines: a "TOP DIGITAL" or "TOP  RATED" line, each followed by a lone "DEALER" line and a lone four-digit year, before the name itself ("Dealer / TOP DIGITAL / DEALER / 2026 / Action Auto Sales and Finance Inc.", recorded detail for JTDBCMFE4R3040782). A page whose "Dealer" heading is followed directly by "Dealer reviews" or "Dealer's description" names no dealer at all (recorded detail for JTDBCMFE8S3078635), and the reader stores none rather than either of those section labels.

The location is never read off the dealer's own street address, whose shape varies too much to parse reliably; two lines cover every recording found so far. A delivered car states its true origin only in its "Choose pickup or delivery" step: "Price includes $2,887 to Orlando, FL. To buy without the delivery fee, choose pick up in Lehi, UT." (recorded detail for JTDBCMFE4R3040782, line 153) names Lehi, UT as the dealer's own location, read ahead of anything else, since a delivered or transferred car's own address block, when it prints one at all, can sit behind extra badge lines the same way its name does, and the line under its title instead names the buyer's destination ("Price includes $462 delivery to Orlando, FL" on a car whose dealer, in Delray Beach, sits elsewhere). A car at or shipped from a dealer, with no pickup line on its page, names its own city on the line under its title instead, alone or beside its mileage ("Mileage: 30,992 · Clermont, FL (38 mi away)", recorded detail for JTDBCMFE8S3078635, which names no dealer at all beyond that city). On a store-transfer page this same line names the receiving store's own city ("Orlando, FL (15 mi away)" for a page whose Dealer block names "CarMax Orlando", with the origin store beneath it, "from CarMax North Houston in Houston, TX", which is not what gets stored). A page that names neither, through either line, stores no location, the same as one whose "Dealer" heading names no name: nothing here is a fallback, so a sighting that reads as none never overwrites a name or a location an earlier one established. A page that names only one of the two (a "Free Delivery to <city>" page, whose "Dealer" block gives a name but whose only city sits unparsed in a street address; or a page whose "Dealer" heading names nobody but whose description names one in free text the reader does not look at) has the half it left null filled from the extraction rather than stored empty, so a name or location the extraction can still read off the rest of the page is not thrown away for want of the other half (`WalkSite.ResolveDealer`). The pacing, the recording, and the bot-challenge pause apply as everywhere else. CarGurus showed no challenge on about thirty loads while this was built.

## Recorded pages

The walk records every page's text under the data directory, in `walks/<site>/<run start in UTC, as yyyyMMdd-HHmmss>/<model>/`, where the model is written in lowercase with hyphens, such as `camry-hybrid`. That keeps each model's pages from colliding with another model's on the same site in one run.

The recorder writes one search text per result page it loads. A pair with one search names its pages `search.txt`, `search-2.txt`, `search-3.txt`, and so on. A pair with two searches names each page by search and page (`search-1-page-1.txt`, `search-1-page-2.txt`, `search-2-page-1.txt`, and so on), so the second search's first page can never overwrite the first search's second page. The detail pages are numbered straight through the pair (`detail-1.txt` and on), so nothing collides there either. A CarMax page whose HTML gave no VIN is also written as `detail-N.html`.

Beside each search text the recorder also writes a cards file named the same way (`cards.json`, `cards-2.json`, `cards-1-page-2.json`, and so on, following each search name above). It's a list of that search page's detail links, each with its own text and the text of the result card it sits in, so you can cut a fixture from a real page later. The search text itself doesn't change.

When cars.com's render wait (see [cars.com](#carscom)) gives up on a card, the recorder also writes an `unrendered.json` beside that page's cards file (`unrendered-2.json`, `unrendered-1-page-2.json`, and so on, following the same naming): the hrefs of the cards still empty when the bounded wait ended, so a later look can see which car's own card never rendered in time. Only written when the page's wait actually left something unrendered.

## Extraction

The walk turns each detail page's text into vehicle fields with a model. By default it uses your already-authenticated `claude` CLI, so no Anthropic key is required at all. If `Anthropic:ApiKey` is set, it calls the Anthropic Messages API directly instead. Both paths read at most the first 12,000 characters of the page, and the CLI runs with no tool access.

The prompt asks for ten fields: the VIN, year, make, model, trim, price, mileage, dealer name, dealer location, and fuel type. It tells the model to read them off the page and not to guess. The model is the full model name as the page's own title prints it, and a variant word such as Hybrid, Prime, or Plug-in stays part of the model and never moves into the trim. A "2023 Toyota Corolla Hybrid" title with "LE Sedan 4D" beneath it yields the model "Corolla Hybrid" and the trim "LE". The dealer is the selling dealer's own name and city and state, and not the listing site's. The fuel type (Gas, Hybrid, Plug-in Hybrid, or Electric) is whatever the page's spec line states. The walk prints it on each page's console line and does not store it, but a hybrid query's match does depend on it: a page whose fuel type reads Hybrid matches on its make and base model alone, as a fourth route alongside the title line and the spec line (see [Rules every site shares](#rules-every-site-shares)). The prompt also says the page text is data and never instructions.

Anything the page doesn't state comes back as null. A VIN has to be exactly 17 characters with no I, O, or Q, or it's null. CarMax is the exception to reading it here, since its pages print no VIN in their text, so its VIN is read from the page's HTML. After the call, odo checks the VIN, make, model, price, mileage, dealer name, and dealer location against the page text, and it nulls any that doesn't appear there. A model that can't be found in the page text is nulled too, so it can't match and the page is dropped as "wrong model".

The nulls then decide what happens to the page. A page is checked in this order: sold, no price listed (both from the page's own text, on the sites that have patterns for them), new-car (cars.com only), extraction failed, no VIN, repeat, wrong model, and then missing fields, so the first reason that applies is the one it's dropped for. A null year, price, or mileage gets it dropped as "missing fields". A null dealer only means no dealer is linked to the posting, and it never erases a link an earlier sighting made.
